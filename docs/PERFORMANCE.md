# 性能与等待时间

## 1. 实测基线

环境：2C / 1.9GB 云服务器，视频《西北某层基院检察一名助理的投稿》2 分 21 秒，ASR + OCR + LLM 全链路。

| 阶段 | 优化前耗时 |
| --- | --- |
| 视频解析（ASR + OCR，首次） | 26–50s |
| Planner | 9–14s |
| Executor 生成 | 55–132s |
| Critic | 12–26s |
| Critic 触发的第二轮（Replanner + Executor + Critic） | +90–120s |
| **总计** | **约 200s** |

同一视频、换一个新目标（三点总结）优化后实测：**123s**，下降约 **38%**。

## 2. 已实施的优化（不改变事实与总结深度）

| 优化 | 做法 | 为什么不影响质量 |
| --- | --- | --- |
| ASR 分片并发 | 60s 分片并行调用（默认 3 并发），结果按分片序号回填 | 转写内容与串行完全一致，只是把网络等待重叠 |
| Critic 建议分流 | 只有事实证据、目标覆盖、结构缺失才触发重跑；纯风格 `feedback` 保留为建议并放行 | 事实校验（EvidenceAuditor）与结构校验不变；不再为措辞重写整篇 |
| 证据去重 prompt | 同一句原文只允许在 evidence 出现一次，结论/建议避免复述 | 减少重复输出，不减少有效信息 |
| 上下文复用（已有） | 同一内容哈希只跑一次 ASR/OCR；换目标直接复用 | 完全相同的内容，零质量损失 |
| ASR / OCR 并行（已有） | 两条分支同时执行 | 两条分支互不依赖 |
| 结果 / Plan 缓存（已有） | 同视频同目标直接复用；Plan 按目标缓存 | 相同输入返回相同结果 |

## 3. 可调参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `AI_ASR_SEGMENT_CONCURRENCY` | `3` | ASR 分片并发，1–8；过高可能触发供应商 429 |
| `AGENT_CRITIC_ADVISORY_PASS` | `true` | `false` 恢复“所有 Critic feedback 都重跑”的严格模式 |
| `AGENT_MAX_ROUNDS` | `2` | 设为 `1` 可再省一轮，但会保留“未通过 Critic”的警告 |
| `AGENT_MAX_DURATION_MS` | `600000` | 单任务时间预算；太小会在慢模型上被截断 |
| `AGENT_MAX_ESTIMATED_TOKENS` | `200000` | 单任务 token 预算 |
| `LLM_MODEL` | `deepseek-ai/DeepSeek-V3.2` | Executor 质量的主要来源，换小模型会降质量 |
| `ASR_MODEL` | `Qwen/Qwen3-ASR-1.7B` | 识别准确率决定证据能否通过校验 |

## 4. 下一步可做（仍不影响总结质量）

1. **上传后预取上下文**：上传完成即后台跑 ASR/OCR，用户点分析时直接命中缓存，可省首次 26–50s。
2. **流式输出**：总耗时不变，但结果逐段出现，感知等待明显降低。
3. **Planner/Critic 用更快的结构化小模型**：这两个阶段只输出 JSON 检查结果，Executor 保持强模型；可省约 10–20s，需做小样本质量对比。
4. **减少证据重试**：ASR 专有名词/时间戳边界更准时，第一轮就能通过，避免 40–60s 的第二轮。
5. **硬件**：4C8G 起；Qdrant 重新启用后长视频检索更稳（但 1.9GB 内存下不建议开）。
